# Variatio

Knowledge graph-guided generator of adaptive educational content. It produces **learning items** (exercises, problems, assessment tasks) grounded in a curriculum graph, with a single pipeline serving two use cases: autonomous student practice and teacher-facing exam preparation.

The domain is education; **the subject is a parameter**. Prompts reason about learning objectives, prior knowledge and cognitive load — what is taught comes from each instance's artifacts, never from the code.

Developed as the final thesis (TFM) of a Master's degree in Artificial Intelligence.

> **This branch is the core system**: the library and its command line, with no web interface,
> no API, no database and no evaluation harness. The complete system lives on the
> **`variatio-web`** branch — see [Using the web interface](#using-the-web-interface).

## What it does

- **Builds an instance from real documents.** From lecture notes, exercises and exams (`.pdf`, `.docx`, `.pptx`, `.md`, `.txt`), the builders produce the artifacts that define an instance: the knowledge graph (extraction → cleaning → domains → relations → curation), the exemplars bank and the exemplars profile (the item schema). Documents are transcribed page by page with a vision model and cached by content, so the same document is never read twice; a hand-corrected page beats the model and survives every later build.
- **Generates grounded items, not loose text.** Every commission draws on few-shot examples from the bank, on the prerequisite scaffolding derived from the graph (transitive closure: what is assumed known, what is not yet taught) and on the course curriculum — the list of concepts already covered. A guardrail model and an admissibility judge screen the free-text instructions, every item is validated against the profile's schema, and a batch of checks decides whether an item is returned or asked for again.
- **Serves several subjects at once.** Each *workspace* is a complete instance: artifacts, cache and raw documents under `workspaces/<slug>/`. There is no default instance — `--workspace` is required everywhere.
- **Speaks the subject's language.** A workspace is built in Spanish or in English, chosen at creation: the prompts, the strings the code composes and the graph's own relation vocabulary all follow it.

## How it works

### The four artifacts

Each instance is defined in `workspaces/<slug>/instance/`:

| Artifact | Contents |
|---|---|
| `knowledge_graph.json` | The curriculum graph: concepts by domain, typed relations (prerequisite, subsumption, association), reviewed taggability. |
| `exemplars_bank.json` | Real exemplars extracted from the corpus, tagged by concept. |
| `exemplars_profile.json` | The content schema: fields, per-field guidance, generation rules, one difficulty criterion per modality. It instantiates the use case. |
| `content_context.json` | The subject in prose (matter, level, language of instruction), interpolated into every prompt. |

Each one has its `_autogenerated` draft (what the builder writes) and its curated version (what a person approves); the curated one always wins.

### The pipeline

```
transcribe  →  raw/ → markdown pages (one vision-model call per page, cached by content)
build       →  raw/ → artifacts (LLM extraction, cleaning, curation)
init        →  loads the instance, describes and embeds the concepts, tags the bank
generate    →  few-shot + prerequisite scaffolding + curriculum → validated items
```

Transcribing ahead of a build is an accelerator and never a gate: every builder keeps its own conversion phase, hitting the cache when the work is done and doing it when it is not.

The retrieval index embeds **LLM-written concept descriptions grounded in the corpus**, never names, fused with exemplar centroids; the tagger combines that prefilter with an LLM verification pass that sees descriptions and relations, not bare names.

### Inference engines

- **`ollama`** (default): a 100 % local, open-weights stack at `OLLAMA_HOST` — directly or through an SSH tunnel opened outside the process.
- **`cerebras+ollama`** (optional): routes the models Cerebras serves to its API while the guardrail and the embedder stay local. It includes a quota limiter measured against the real API — rolling per-minute and per-day windows, per-phase accounting, a booked claim per call, and either a cancellable wait or a readable refusal.

Every pipeline phase declares its own model, context window and reasoning level; `config.json` holds one complete profile per engine, so switching engine swaps the whole set and switching back recovers the previous one untouched.

## Getting started

Requirements: Python 3.10, [`uv`](https://docs.astral.sh/uv/) and a reachable Ollama server. Building artifacts from `.docx`/`.pptx` sources also needs LibreOffice on the `PATH`, which is what rasterises the EMF/WMF metafiles those formats embed.

```bash
uv sync                       # the pipeline plus the authoring dependencies
```

The runtime core is 57 MB in a clean environment. Docling adds ~700 MB and is only needed
to turn documents into artifacts, so it sits behind the `builders` extra and is imported
lazily: `uv sync --no-dev` gives the runtime alone, and a runtime-only consumer that
reaches for a builder gets a clear `ImportError` naming the extra.

A workspace is a directory. Create one, drop the source documents into its two raw slots, and build:

```bash
mkdir -p workspaces/<slug>/raw/raw_corpus workspaces/<slug>/raw/raw_exemplars_bank
#   raw_corpus/         → lecture notes and theory: what the knowledge graph is extracted from
#   raw_exemplars_bank/ → exercises and exams: what the profile and the bank are extracted from
uv run variatio all --workspace <slug>
```

The repository ships no instance: `workspaces/` is ignored in full, and each installation holds its own.

### CLI

```bash
uv run variatio transcribe --workspace <slug> [--slot corpus|exemplars|all]
uv run variatio build      --workspace <slug>   # create the missing artifacts from raw/
uv run variatio init       --workspace <slug>   # load the instance, tag the bank, warm the indices
uv run variatio generate   --workspace <slug> -n 3 --concepts "Recursividad" --item-type <modality>
uv run variatio all        --workspace <slug>   # build what is missing, then init and generate
```

`generate` also takes `--fixed FIELD=VALUE` (repeatable), `--curriculum` and `--instructions`.

## Using the web interface

The web half — a FastAPI + PostgreSQL API, a React front end and the study's blind
three-arm comparison — is not on this branch. It lives on **`variatio-web`**, which carries
this same library plus `server/`, `evaluation/`, `web/` and the Alembic migrations.

```bash
git switch variatio-web
uv sync                            # now installs the server extra as well
docker compose up -d postgres      # PostgreSQL 16 on :5432, credentials in .env
uv run alembic upgrade head        # create the schema
uv run system create-workspace <slug> --name "<Subject>" --language es
uv run system create-user --username <name> --admin --workspace <slug>
uv run system                      # the API on :8000
```

The API serves the front end's build output, so build it once — and again after every
change to `web/`:

```bash
cd web && pnpm install && pnpm build
```

For front-end development, `pnpm dev` runs Vite with hot reload and proxies the API.

An instance built on this branch moves to the other one unchanged, in either direction: no
cache key is a path, so a `workspaces/<slug>/` directory is portable, and
`uv run system import-instance --slug <slug>` is what registers one that already exists on
disk with the database.

## Tests

```bash
uv run pytest              # the suite (the corpus and model tests are deselected)
uv run pytest tests/core   # each subsystem runs on its own
uv run pytest -m corpus    # statistical quality of a real graph build
uv run pytest -m model     # the admissibility judge against a live Ollama
```

The suite is split by subject, one directory per subsystem. The `corpus` and `model` tests
measure a real installation rather than the code, so they name the workspace they open
(`VARIATIO_MODEL_WORKSPACE`) and skip when it is not there.

## Repository layout

```
variatio/
  core/         inference, progress, paths, JSON I/O, the Cerebras ledger
  instance/     the loaders of the four artifacts
  builders/     raw → artifacts: document plumbing, the three builders
  runtime/      artifacts → items: generator, tagger, embedder, screening, checks
  entrypoints/  the public API — everything that takes a Workspace
  prompts/      one set per language (es / en), one module per family
  wording/      the strings the code composes, in the workspace's language
  settings/     the settings registry, with the measurement beside each value
  cli.py        the command line
tests/          one directory per subsystem
workspaces/     the instances, one directory per slug (git-ignored)
```

Two rules make the package legible and both are one `grep`: only `entrypoints/` takes a
`Workspace`, and only `builders/` and `runtime/` call the model. Two more are pinned by
tests: importing `variatio` pulls in neither Docling nor torch — the authoring dependencies
are lazy behind the `builders` extra — and secrets live only in `.env`, never in
`config.json`.

## Configuration

Every setting is declared in `variatio/settings/registry/`, each with its measured
documentation and its cost of change (`Impact`), and resolves with precedence
*default < `config.json` < environment*. Deleting `config.json` is safe — everything falls
back to the registry defaults.
